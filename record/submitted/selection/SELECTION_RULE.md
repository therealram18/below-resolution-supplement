# Pre-registered dataset-config selection rule — Result 2 (protocol-injected variance)

**Version 2. Date written: 2026-09-12, same day as v1, after an adversarial review found flaws in v1. Written and committed before any model inference for this experiment has been run — v1 was also never run against a model, so nothing here was chosen after seeing results.** See "Revision history" at the end for exactly what changed and why. v1's files are kept, renamed, in this folder: `select_configs_v1.py`, `SELECTION_RULE_v1.md`, `selected_configs_v1.json`.

## Purpose

Result 2 of the FMTS paper is the one part of the paper that needs a GPU: we run
four real forecasting models ourselves and see how much their scores move when
we change one setting (context length — how many past time steps the model is
shown before it forecasts). That check only needs a subset of the 97
dataset-configs on the GIFT-Eval leaderboard, not all of them. This document
fixes, in advance, exactly which 12 configs we will use and exactly how they
were chosen, so nobody can look at results first and then pick configs that
make the story look better. The rule below is implemented in
`select_configs.py` in this same folder, and the output —
`selected_configs.json` — is generated by running that script, not by hand.

## The universe: 97 configs, 28 base datasets

The GIFT-Eval leaderboard evaluates every model on 97 "configs." Each config
is named `base_dataset/frequency/term`, for example `m4_weekly/W/short` (base
dataset `m4_weekly`, weekly frequency, short forecast horizon). We read the
list of 97 config names straight from the `dataset` column of one model's
results file in the pinned snapshot
(`snapshot_2026-09-07/results/seasonal_naive/all_results.csv`, which we
verified has exactly 97 rows, all distinct). We only ever read config
*names* from this file — never the error/score columns next to them.

The 97 configs come from 28 distinct base datasets, and split into three
terms (forecast horizon lengths):

- **short**: 55 configs
- **medium**: 21 configs
- **long**: 21 configs

## Eligibility filter (new in v2 — the blocking fix)

The experiment's whole point is to compare two context-length settings: each
model's own documented default, versus a fixed 512 time steps for every
model. That comparison can only show something if the two settings actually
differ for the data being shown to the model. Some of GIFT-Eval's configs use
series far shorter than 512 points — both context-length settings end up
truncated to "the whole series," so the model sees the identical history
either way and the config measures nothing.

v1 did not check for this, and three of its twelve picked configs turned out
to be no-ops: `m4_yearly/A/short` (median series length 35 points),
`solar/W/short` (median 52 — in fact every one of its 137 series is exactly
52 points long), and `m4_monthly/M/short` (median 220). All three are far
below 512, let alone the model's own defaults (which are typically larger
still).

**The rule:** a config is eligible only if the median series length of its
underlying (dataset, frequency) data is **at least 1024** points — roughly
double 512, so the two context-length settings are guaranteed to differ by
at least ~2x for the median series in an eligible config, not just scrape by.
Median length, not mean, so a handful of unusually long series in an
otherwise-short dataset can't make it eligible by accident.

**How it's computed.** `compute_median_lengths.py` reads every downloaded
data file under `harness/data/` (the raw arrow files; each series' length is
the size of its `target` column) and writes one median length, series count,
and resolved directory per config to `config_median_lengths.json`. That
script needs `pyarrow`, which is outside the plain standard library, so it's
run with the interpreter that has it:
`harness/envs/chronos_bolt_base/bin/python3 compute_median_lengths.py`.
`select_configs.py` itself only ever reads the resulting JSON with the
standard library's own `json` module, so the actual selection stays
pure-stdlib and deterministic.

**Mapping config names to data directories.** Config base-dataset names
mostly match the folder names under `harness/data/` directly, but seven
don't — the downloaded data keeps the original source dataset's name. The
mapping (config name → directory name) is GIFT-Eval's own, taken from the
`pretty_names` dictionary that appears in every model-submission notebook
under `harness/gift-eval/notebooks/` (e.g. `timesfm.ipynb`), and confirmed
against the actual directory listing:

## Domain spread (new in v2)

GIFT-Eval itself assigns each of the 28 base datasets to one of seven
domains (Econ/Fin, Energy, Healthcare, Nature, Sales, Transport,
Web/CloudOps) — the same labels used on the public leaderboard, read from
`harness/gift-eval/notebooks/dataset_properties.json`. v1 never looked at
domain at all, so it was possible (and did happen) for the 12 picks to lean
heavily on one or two domains just by chance of the shuffle. v2 adds domain
as a *soft* preference layered on top of the *hard* rule that all 12 picks
must have distinct base datasets — domain never overrides that.

## The selection rule, exactly as implemented

1. **Filter to eligible configs first.** Everything below only ever looks at
   the 70 eligible configs; the 27 ineligible ones are set aside entirely,
   including for the term-allocation arithmetic.

2. **Split 12 slots across the three terms, proportionally to ELIGIBLE
   counts (not the 97-config totals).** Each term gets `12 × (its share of
   the 70 eligible configs)`, rounded using the largest-remainder method
   (give every term its rounded-down share first, then hand out the few
   slots left over to the terms with the largest leftover fraction, highest
   first; ties broken alphabetically by term name). Doing the arithmetic:

   | term | eligible (of 70) | exact share of 12 | rounded down | leftover fraction | final slots |
   |---|---|---|---|---|---|
   | short | 28 | 4.8000 | 4 | 0.8000 | **5** |
   | medium | 21 | 3.6000 | 3 | 0.6000 | **3** |
   | long | 21 | 3.6000 | 3 | 0.6000 | **4** |

   Two slots are left over after rounding down (4+3+3=10 of 12). Short's
   leftover fraction (0.8000) is the single largest, so it claims the first
   extra slot outright. Medium and long are tied at 0.6000; the alphabetical
   tie-break gives the second extra slot to whichever name sorts first —
   "long" sorts before "medium" — so long gets it. Final:
   **short = 5, medium = 3, long = 4** (sums to 12).

3. **Process the three terms in a fixed order: short, then medium, then
   long.** This order matters because a base dataset (and, softly, a domain)
   used in an earlier term can't be reused the same way in a later one, so
   it has to be fixed in advance rather than left to chance.

4. **Sort each term's eligible configs alphabetically, then shuffle with the
   same seed.** For each term, take that term's eligible configs, sort them
   alphabetically by config name, and *then* shuffle with
   `random.Random(20260912).shuffle(...)`. Sorting before shuffling is what
   makes the result depend only on the seed and the *set* of eligible
   configs for that term — not on whatever order they happened to appear in
   the source CSV. We verified this directly: running the script against a
   copy of the snapshot CSV with its rows shuffled into a different order
   produces the exact same 12 selected configs.

5. **Walk the shuffled list and greedily pick configs, subject to three
   rules, tried in order — pass 2 only runs if pass 1 didn't fill the term's
   slots, pass 3 only if pass 2 still didn't:**
   - **(a) Distinct base datasets, required, global, never relaxed.** A
     config can only be picked if its base dataset has not already been used
     by *any* previously selected config, in this term or an earlier one.
     This is what guarantees the final 12 configs come from 12 different
     base datasets.
   - **Pass 1 — distinct domain (global) and distinct frequency (within the
     term), both preferred.** Take a config only if its domain hasn't been
     used by any previously selected config yet, *and* its frequency hasn't
     already been picked within this term.
   - **Pass 2 — distinct frequency only.** If the term's slots aren't all
     filled after pass 1, take a config whose frequency is still new within
     this term, but now allow its domain to repeat one already selected.
   - **Pass 3 — anything left, subject only to rule (a).** If slots still
     remain, fill them from whatever's left, keeping only the base-dataset
     rule.

6. Stop once all 12 slots are filled. Write the result — including the
   allocation math, every selected config's base dataset, frequency, term,
   domain, and median series length, plus the md5 of the two input files —
   to `selected_configs.json`, and print the same to the screen.

No exclusion or inclusion in this rule depends on any model's score, error,
or rank. Beyond the length filter (which only looks at how much data exists,
not any model's performance on it), the rule only ever looks at config
*names*, domains, and data lengths — nothing about how well any model does.
Running `select_configs.py` twice, on the same two input files, produces
byte-identical output (verified: both runs produced `selected_configs.json`
with md5 `32d6a021400e97e7040e0963449761f9`).

## The full pre-registered protocol for the runs themselves

**Models — 4, inference only.** No fine-tuning, no retries, no per-dataset
tuning of any kind. Each model runs once per (config, context-length
setting) pair and whatever number comes out is the number we report.

| model | source |
|---|---|
| Chronos-Bolt-base | `amazon/chronos-bolt-base` |
| Moirai-2.0-R-small | `Salesforce/moirai-2.0-R-small` |
| TimesFM-2.5-200M | `google/timesfm-2.5-200m-pytorch` |
| Toto-Open-Base-1.0 | `Datadog/Toto-Open-Base-1.0` |

**The one thing we deliberately change: context length.** Context length is
how many past time steps a model is shown before it has to forecast the
future. For each model we run it twice per config: once with that model's
own documented default context length, and once with a context length of 512
time steps for every model, so all four models get exactly the same
alternative setting. Nothing else about the run changes between the two
settings. (This is exactly the contrast the v2 eligibility filter protects —
every one of the 12 selected configs now has enough history that "default"
and "512" are genuinely different inputs to the model.)

**Metric.** MASE[0.5] (median-forecast Mean Absolute Scaled Error — the same
error measure, computed the same way, that the GIFT-Eval leaderboard itself
uses) for each of the 12 configs, using GIFT-Eval's own evaluation code, not
a reimplementation.

**Two ways of turning 12 per-config scores into one number per model, both
applied to the same runs (no extra inference for either one):**
1. **Rank against the real leaderboard, then average (relabeled in v2 — see
   below).** For each of our runs, take our measured MASE for that config
   and insert it into the snapshot's published per-config score pool for
   that config (`snapshot_2026-09-07/results/`, 130 models), and record
   where it would rank there. Average that rank over the 12 configs. In
   plain words: where would this run land on the actual leaderboard, under
   each context-length setting, if it were entered as a 131st model. v1
   called this "the same rule the leaderboard displays" — that was wrong; a
   rank among 130 real, independently-run leaderboard models is not the
   same statistic as a rank among our own 4 models on the same 12 configs.
   v2 does not change what gets computed, only how it is described.
2. **Geometric mean of seasonal-naive-scaled MASE — unchanged.** Divide each
   model's MASE by the seasonal-naive model's MASE on that same config, then
   take the geometric mean across the 12 configs.

**What gets reported.** For each model, how much its aggregate score/rank
moves when we switch context length from default to 512 — and whether that
movement is bigger than a sampling-noise band. **In v2, that band is
recomputed specifically for this comparison** (see below), not reused from
Result 1. Both context settings are reported for every model, side by side;
we do not pick whichever one looks better and hide the other.

**Sampling-noise band — recomputed for the 12 configs (new in v2).** v1
compared the 12-config movement against the sampling-noise band already
computed in Result 1, which was built from resampling across all 97
configs. That band is the wrong yardstick for a 12-config number: comparing
a measurement made on 12 configs against noise estimated from 97 would make
real movement look artificially large relative to noise, understating the
true noise by a factor of about √(97/12) ≈ 2.8. v2 instead recomputes the
band by paired bootstrap resampling over exactly these same 12 configs, using
the snapshot's published per-config files (the same 130-model pool used for
the rank statistic above) — resample the 12 configs with replacement, redo
the aggregate statistic, repeat, and take the spread of the result as the
noise band. Because all 12 selected configs come from 12 distinct base
datasets, resampling *configs* here and resampling *dataset-clusters* are
the same operation — there's no cluster of several configs from one base
dataset that bootstrap resampling could accidentally over- or under-weight.

**Descope ladder, pre-committed now, before any run.** If time or hardware
runs out: drop from 4 models to 3, then from 3 to 2 (keeping one
Chronos-family model and one non-Chronos model, so a cut is never mistakable
for avoiding an FMTS organizer's own model). 12 configs is already the
reduced tier — it does not get cut further. If the whole GPU grid fails, the
paper ships without Result 2, as Results 1 and 3 only.

**Disclosure.** Chronos-Bolt-base's own entry on the GIFT-Eval leaderboard is
flagged `testdata_leakage: Yes` in its published config
(`snapshot_2026-09-07/results/chronos_bolt_base/config.json`). We include it
anyway because it is one of the four models named in the frozen paper design
and dropping it would look like cherry-picking after the fact — but the flag
will be disclosed in the paper wherever Chronos-Bolt-base's numbers appear.

## Revision history

**v1 — written 2026-09-12 morning.** First version of this rule: 97 configs,
no eligibility filter, largest-remainder term allocation over all 97, base
dataset uniqueness as the only hard rule, frequency-only 2-pass soft
preference, seed 20260912. Never run against a model.

**v2 — written 2026-09-12, same day, after an adversarial review, before any
model run.** The review found five problems, all fixed above:

1. **Three of the twelve v1 picks could measure nothing.** `m4_yearly/A/short`
   (median series length 35), `solar/W/short` (median 52, literally every
   series), and `m4_monthly/M/short` (median 220) are all far shorter than
   512 time steps, so the "model's default context" vs "512" comparison
   would show the model the same truncated history either way. Fixed by the
   new median-length-≥-1024 eligibility filter, which drops these three plus
   24 more (27 of 97 total, all short-term).
2. **The selection depended on the input CSV's row order**, though v1's own
   text claimed any model's file "would give the same result" — that claim
   was false as written (verified: the shuffle picks different configs from
   a differently-ordered but identical-content CSV). Fixed by sorting each
   term's eligible configs alphabetically before shuffling; the claim is now
   true and re-verified directly against a row-shuffled copy of the CSV.
3. **No domain consideration.** v1's rule could (and did) let the 12 picks
   cluster on a few domains by chance. Fixed by adding domain as a soft,
   three-pass preference (domain+frequency, then frequency-only, then
   unconstrained) layered on top of the unchanged, hard base-dataset-
   uniqueness rule.
4. **The sampling-noise band was the wrong size.** Comparing this
   experiment's 12-config movement against Result 1's 97-config resampling
   band would understate real sampling noise by about √(97/12) ≈ 2.8x. Fixed
   by recomputing the band as a paired bootstrap over exactly the 12 selected
   configs, from the snapshot's own published per-config files.
5. **A 4-model rank was mislabeled as leaderboard-equivalent.** v1 called
   "mean of per-config ranks" "the same rule the leaderboard displays," but
   it ranked only our own 4 models against each other, not against the real
   130-model leaderboard. Fixed by relabeling the statistic honestly: our
   measured MASE is inserted into the snapshot's real per-config score pool
   (130 models) and the rank it would get there is what gets averaged.

## Addendum (2026-09-12, before any model run): what "documented default" means, exactly

For every model, the "default" context length is defined as **the setting used
by GIFT-Eval's own reference notebook for that model — i.e. the recipe that
produced the model's published leaderboard entry**. Concretely: Chronos-Bolt-base
= 2048 (baked into the checkpoint; the notebook feeds full series and the model
truncates to its last 2048 points internally), Moirai-2.0-R-small = 4000
(hardcoded in gift-eval's moirai2 notebook), TimesFM-2.5-200M = full available
history capped at 15360 (the notebook's dynamic recipe), Toto-Open-Base-1.0 =
4096 capped by available history (the notebook's constant).

One known ambiguity, recorded before running: Moirai-2.0-R-small's checkpoint
config reports max_seq_len = 512 even though gift-eval's notebook passes 4000.
If the model internally ignores context beyond 512, then its "default vs 512"
runs will produce identical forecasts — the smoke test checks this directly,
and if they are identical we will report exactly that (the leaderboard recipe's
4000 is cosmetic for this model) rather than swapping in a different setting
after the fact.
