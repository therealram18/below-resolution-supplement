# Pre-registered dataset-config selection rule — Result 2 (protocol-injected variance)

**Date written: 2026-09-12. Written and committed before any model inference for this experiment has been run.**

## Purpose

Result 2 of the FMTS paper is the one part of the paper that needs a GPU: we run
four real forecasting models ourselves and see how much their scores move when
we change one setting (context length — how many past time steps the model is
shown before it forecasts). That check only needs a subset of the 97
dataset-configs on the GIFT-Eval leaderboard, not all of them. This document
fixes, in advance, exactly which 12 configs we will use and exactly how they
were chosen, so nobody can look at results first and then pick configs that
make the story look better. The rule below is implemented in
`select_configs.py` in this same folder, and the output —
`selected_configs.json` — is generated by running that script, not by hand.

## The universe: 97 configs, 28 base datasets

The GIFT-Eval leaderboard evaluates every model on 97 "configs." Each config
is named `base_dataset/frequency/term`, for example `m4_weekly/W/short` (base
dataset `m4_weekly`, weekly frequency, short forecast horizon). We read the
list of 97 config names straight from the `dataset` column of one model's
results file in the pinned snapshot
(`snapshot_2026-09-07/results/seasonal_naive/all_results.csv`, which we
verified has exactly 97 rows, all distinct). We only ever read config
*names* from this file — never the error/score columns next to them. Any
other model's file has the same 97 config names and would give the same
result; we used seasonal_naive's because it's a fixed reference model rather
than a competitor.

The 97 configs come from 28 distinct base datasets, and split into three
terms (forecast horizon lengths):

- **short**: 55 configs
- **medium**: 21 configs
- **long**: 21 configs

## The selection rule, exactly as implemented

1. **Split 12 slots across the three terms, proportionally.** Each term gets
   `12 × (its share of the 97 configs)`, rounded using the largest-remainder
   method (give every term its rounded-down share first, then hand out the
   few slots left over to the terms with the largest leftover fraction,
   highest first). Ties in the leftover fraction are broken alphabetically by
   term name. Doing the arithmetic:

   | term | configs (of 97) | exact share of 12 | rounded down | leftover fraction | extra slot? | final slots |
   |---|---|---|---|---|---|---|
   | short | 55 | 6.8041 | 6 | 0.8041 (highest) | yes | **7** |
   | medium | 21 | 2.5979 | 2 | 0.5979 (tied with long, loses tie-break: "medium" > "long" alphabetically) | no | **2** |
   | long | 21 | 2.5979 | 2 | 0.5979 (tied with medium, wins tie-break: "long" < "medium" alphabetically) | yes | **3** |

   6 + 2 + 2 = 10 slots handed out by rounding down; 2 slots left over; the
   two largest leftover fractions are short (0.8041) and the short/medium
   tie between medium and long. Short claims one by having the single
   largest fraction. The second leftover slot is decided by the alphabetical
   tie-break between medium and long: "long" sorts before "medium", so long
   gets it. Final: **short = 7, medium = 2, long = 3** (sums to 12).

2. **Process the three terms in a fixed order: short, then medium, then
   long.** This order matters because of rule 4 below (a base dataset used in
   an earlier term can't be reused in a later one), so it has to be fixed in
   advance rather than left to chance.

3. **Shuffle each term's configs with the same seed.** For each term, build
   the list of that term's configs and shuffle it with
   `random.Random(20260912).shuffle(...)` — a fresh, identically-seeded
   shuffle per term. Seed `20260912` is today's date, chosen for no reason
   other than being memorable and fixed at the time of writing.

4. **Walk the shuffled list and greedily pick configs, subject to two
   rules:**
   - **(a) Distinct base datasets, required, global.** A config can only be
     picked if its base dataset has not already been used by *any*
     previously selected config, in this term or an earlier one. This is
     what guarantees the final 12 configs come from 12 different base
     datasets — no base dataset contributes more than one config to the
     experiment, which keeps the sample from being dominated by one data
     source with many frequency/term variants.
   - **(b) Distinct frequency within the term, preferred, not required.**
     First pass: only take a config whose frequency (hourly, daily, etc.)
     hasn't already been picked within this term. This spreads each term's
     picks across different frequencies rather than clustering on one. If
     the term's slots aren't filled after this pass (can happen when the
     term has few base datasets left to draw from), a second pass fills the
     rest from the same shuffled order, keeping rule (a) but dropping the
     frequency preference.

5. Stop once all 12 slots are filled. Write the result — including the
   allocation math and every selected config's base dataset, frequency, and
   term — to `selected_configs.json`, plus print the same to the screen.

No exclusion or inclusion in this rule depends on any model's score, error,
or rank. The rule only ever looks at config *names* (`base_dataset`,
`frequency`, `term`) — nothing about how well any model does on them. Running
`select_configs.py` twice, on the same pinned snapshot, produces
byte-identical output (verified: both runs produced the file with md5
`69ffd635998aee43ee79da11486c3b8d`).

## The full pre-registered protocol for the runs themselves

**Models — 4, inference only.** No fine-tuning, no retries, no per-dataset
tuning of any kind. Each model runs once per (config, context-length
setting) pair and whatever number comes out is the number we report.

| model | source |
|---|---|
| Chronos-Bolt-base | `amazon/chronos-bolt-base` |
| Moirai-2.0-R-small | `Salesforce/moirai-2.0-R-small` |
| TimesFM-2.5-200M | `google/timesfm-2.5-200m-pytorch` |
| Toto-Open-Base-1.0 | `Datadog/Toto-Open-Base-1.0` |

**The one thing we deliberately change: context length.** Context length is
how many past time steps a model is shown before it has to forecast the
future. For each model we run it twice per config: once with that model's
own documented default context length, and once with a context length of 512
time steps for every model, so all four models get exactly the same
alternative setting. Nothing else about the run changes between the two
settings.

**Metric.** MASE[0.5] (median-forecast Mean Absolute Scaled Error — the same
error measure, computed the same way, that the GIFT-Eval leaderboard itself
uses) for each of the 12 configs, using GIFT-Eval's own evaluation code, not
a reimplementation.

**Two ways of turning 12 per-config scores into one number per model, both
applied to the same runs (no extra inference for either one):**
1. **Mean of per-config ranks** — the same rule the leaderboard displays.
2. **Geometric mean of seasonal-naive-scaled MASE** — divide each model's
   MASE by the seasonal-naive model's MASE on that same config, then take
   the geometric mean across the 12 configs.

**What gets reported.** For each model, how much its aggregate score/rank
moves when we switch context length from default to 512 — and whether that
movement is bigger than the sampling-noise band already computed in Result 1
(the leaderboard-resampling result, which needs no GPU). Both context
settings are reported for every model, side by side; we do not pick whichever
one looks better and hide the other.

**Descope ladder, pre-committed now, before any run.** If time or hardware
runs out: drop from 4 models to 3, then from 3 to 2 (keeping one
Chronos-family model and one non-Chronos model, so a cut is never mistakable
for avoiding an FMTS organizer's own model). 12 configs is already the
reduced tier — it does not get cut further. If the whole GPU grid fails, the
paper ships without Result 2, as Results 1 and 3 only.

**Disclosure.** Chronos-Bolt-base's own entry on the GIFT-Eval leaderboard is
flagged `testdata_leakage: Yes` in its published config
(`snapshot_2026-09-07/results/chronos_bolt_base/config.json`). We include it
anyway because it is one of the four models named in the frozen paper design
and dropping it would look like cherry-picking after the fact — but the flag
will be disclosed in the paper wherever Chronos-Bolt-base's numbers appear.
